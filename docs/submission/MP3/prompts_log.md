# 프롬프트 기록

AI 도구와 논의하면서 정한 주요 결정 사항입니다. 지시와 수행 내역이 아니라, 논의 끝에 채택하거나 고친 결정만 담았습니다.
각 결정에는 논의의 출발이 된 주요 프롬프트의 요지, AI 응답, 그 응답을 어떻게 채택·수정했는지(최종 결정)와 이유를 적었습니다.

- **사용 도구**: Claude Code (Anthropic). 다른 AI 도구는 사용하지 않았습니다.
- **프롬프트**: 작업을 시킨 문장이 아니라 무엇을 검토하고 판단하려 했는지를 요약했습니다.
- **구분**: 채택은 AI 응답을 받아들인 것, 수정은 조건을 바꿔 받아들인 것, 기각 후 수정은 AI 응답을 받아들이지 않고 다른 방법을 정한 것, 보류는 이번에 하지 않기로 한 것입니다.
- **구성**: 단계마다 앞 단계의 결정에 그 단계의 결정을 더합니다.

## MP1 결정 사항

### 1. 구조 단순화 — 수정

- **프롬프트**: "구현체가 하나이고 추가 구현 계획도 없는데 인터페이스를 유지할 실질적인 이점이 있을까요? 파일 수를 줄이는 게 목적이 아니라, 필요한 책임 분리는 지키면서 실행 흐름을 설명하기 쉽게 만드는 게 목적입니다."
- **AI 응답**: 교체 계획이 없는 인터페이스 5개는 제거해도 된다. Dart는 모든 클래스가 인터페이스 역할을 하므로 테스트 대역은 구현 클래스를 `implements`해서 만들면 된다.
- **최종 결정**: 인터페이스는 제거하되, ViewModel·Controller 같은 새 계층은 넣지 않고 기존 Page + Service 구조와 실제 책임 분리는 유지합니다.
- **이유**: 과제 범위와 기술이 확정되어 있어 교체를 위한 추상화가 필요 없고, 계층이 적어야 실행 흐름을 설명하기 쉽습니다.

### 2. 예외와 오류 문구 — 채택

- **프롬프트**: "분석 오류는 공통 타입으로 묶되 권한·입력·저장 오류의 구분은 남기는 게 맞을까요? 검토에서 나온 권한 안내 문구 오류와 플랫폼 원문 노출 문제도 같이 봐야 할 것 같습니다."
- **AI 응답**: 사용자에게 그대로 보여줄 수 있는 `message`를 가진 `AppException`을 기반으로 예외를 `domain/exceptions.dart`에 모으고, 권한 거부(`ImagePermissionDeniedException`)와 그 밖의 입력 실패(`ImageInputUnavailableException`)를 나눈다. 플랫폼 원문 대신 한국어 안내를 보여주고, 권한 문구는 거부된 경로에 맞춘다.
- **최종 결정**: 제안대로 적용합니다. 화면에는 사용자용 한국어 문구만 표시합니다.
- **이유**: 권한 거부는 설정으로, 입력 실패는 다시 시도로 안내해야 해서 사용자가 할 일이 다르고, 영어 원문은 사용자에게 도움이 되지 않습니다.

### 3. 권한 요청 방식 — 채택

- **프롬프트**: "에뮬레이터에서 권한 거부가 재현되지 않는데, 과제가 요구하는 권한 요청 흐름을 실제로 보여주려면 무엇이 빠져 있는 걸까요?"
- **AI 응답**: 매니페스트에 `CAMERA`가 선언되지 않아 시스템이 권한을 묻지 않는 것이므로 선언을 추가한다. 카메라가 없는 기기도 설치되도록 `android.hardware.camera`는 `required="false"`로 둔다. Android 갤러리는 시스템 선택기가 고른 사진만 넘겨주므로 저장소 권한은 선언하지 않는다.
- **최종 결정**: 제안대로 적용합니다. 권한은 앱 시작 시가 아니라 사용자가 "카메라로 촬영"을 고른 시점에 요청합니다.
- **이유**: 필요한 순간에 필요한 권한만 요청해야 사용자가 이유를 이해합니다.

### 4. 권한 거부 안내와 설정 이동 — 수정

- **프롬프트**: "MP1의 "거부 시 안내 화면(설정 이동 안내 포함)" 기준에 비춰 보면, 창만 닫는 지금의 설정 버튼으로 충분할까요?"
- **AI 응답**: 설정 화면을 실제로 여는 방법과 문구로 경로만 안내하는 방법이 있다. 실제로 열려면 `app_settings` 패키지를 쓴다.
- **최종 결정**: 둘 중 하나가 아니라 둘 다 적용합니다. 버튼으로 이 앱의 설정 화면을 열고, 안내 문구에도 "설정 > 권한 > 카메라" 경로를 적습니다. 설정을 열지 못하면 직접 변경하라고 안내합니다.
- **이유**: 한 번 거부하면 OS가 다시 묻지 않을 수 있어 설정 이동이 유일한 복구 경로이고, 설정 화면이 열리지 않는 기기에서도 길을 알려줘야 합니다.

### 5. 권한 설명 문구 위치 — 채택

- **프롬프트**: ""권한이 왜 필요한지 설명하는 문구"를 별도 화면 없이 권한을 요청하기 직전에 보여줄 수 있는 자리는 어디일까요?"
- **AI 응답**: 시스템 권한 대화상자가 뜨기 직전 단계인 사진 가져오기 시트의 각 항목 아래에 이유를 적는다.
- **최종 결정**: 카메라 항목에 "촬영을 위해 카메라 권한을 요청해요. 사진은 기기 안에서만 사용합니다.", 갤러리 항목에 "직접 고른 사진 한 장만 앱에 전달됩니다."를 표시합니다.
- **이유**: 별도 설명 화면을 추가하지 않고도 요청 직전에 이유를 알릴 수 있습니다.

### 6. 단계별 제출물 구성 — 기각 후 수정

- **프롬프트**: "MP1과 MP2는 단계별로 제출하는데, 최종 코드를 그대로 낼까요, 단계 범위만 남긴 소스를 낼까요? 단계가 올라갈수록 코드와 문서가 더해지기만 하는 구조로 맞출 수 있을까요?"
- **AI 응답**: 최종 코드를 그대로 제출하고 README에서 단계별 범위만 설명한다. 이후 단계별 소스를 비교한 뒤에는, 앞 단계에만 있는 것을 루트로 옮기고 다음 단계에서 삭제만 해서 앞 단계를 만들자고 제안했다.
- **최종 결정**: 첫 제안은 받아들이지 않았습니다. 단계마다 그 단계 범위의 소스를 제출하되, MP3는 루트와 같게 두고 MP2는 MP3에서, MP1은 MP2에서 다음 단계의 코드를 삭제만 해서 만듭니다. README와 이 기록도 같은 방식으로 앞 단계 내용에 더해 갑니다. 스크린샷은 제출 규칙(한 폴더, 화면 순서 번호, 최대 12장)에 맞춰 단계마다 `screenshots/` 한 폴더에 모으고, 12장을 넘는 MP3는 앞 단계 화면을 일부만 남깁니다. 단계마다 평가 기준은 그대로 충족해야 합니다.
- **이유**: 앞 단계에서 보이던 기능이 다음 단계에서 사라지거나 같은 코드가 단계마다 다르면, 이어서 개발했다고 설명하기 어렵습니다.

## MP2 결정 사항

### 7. 선택 분석 기능 — 수정

- **프롬프트**: "과제는 분석 기능 택1인데 텍스트 인식과 사물 분류가 모두 구현되어 있습니다. 사과 오분류 문제를 고려하면 어느 쪽을 선택 기능으로 내세우고, 다른 쪽은 어떻게 설명해야 할까요?"
- **AI 응답**: 사물 분류에 오분류 문제가 있으므로 텍스트 인식을 주 기능으로, 사물 분류를 추가 기능으로 적는다.
- **최종 결정**: 텍스트 인식을 선택 기능으로 적고, 사물 분류는 삭제하지 않되 "구현은 끝났으나 모델 정확도 때문에 수정이 필요하다"고만 적습니다.
- **이유**: 동작은 하지만 결과를 믿을 수 없는 기능을 완성된 기능처럼 내세우지 않기 위해서입니다.

### 8. 모델 결과 표시 — 채택

- **프롬프트**: "분류 결과를 "사과"로 바꿔 보여주는 하드코딩을 두는 게 맞을까요? 모델이 실제로 낸 라벨과 신뢰도를 그대로 보여주는 쪽이 낫지 않을까요?"
- **AI 응답**: `Granny Smith`를 `사과`로 바꾸는 하드코딩을 삭제하고, 다른 라벨에 비슷한 처리가 없는지 확인했다. 하드코딩에 맞춰져 있던 테스트는 실제 모델 출력 기준으로 바꾼다.
- **최종 결정**: 변환을 삭제하고, 빨간 사과가 석류로 분류되는 문제도 코드로 보정하지 않습니다. 정확도 문제는 문서에 기록합니다.
- **이유**: 특정 사례만 맞히는 보정은 모델의 실제 성능을 가리고 다른 사진에서 새 오류를 만듭니다.

### 9. 인식 불가 처리 — 채택

- **프롬프트**: "글자가 없는 사진에서 "분석 실패"라고 뜨는데, "인식 불가를 오류가 아닌 안내로 처리하라"는 기준에 맞는 표현일까요?"
- **AI 응답**: 인식할 수 없는 사진은 고장이 아니라 정상적인 결과이므로 배지를 **인식 불가**로 바꾸고 "글자가 또렷하게 보이는 사진으로 다시 시도해 주세요."를 덧붙인다. 예상하지 못한 오류에만 **분석 실패**를 쓴다.
- **최종 결정**: 제안대로 적용합니다. 텍스트 인식과 사물 분류의 실패는 `AnalysisException` 하나로 다루고, 오류 원문은 화면에 보이지 않게 합니다.
- **이유**: 과제가 인식 불가를 오류가 아닌 안내로 처리하라고 요구하며, 사용자에게는 다음에 할 일이 필요합니다.

### 10. 처리 시간 측정 — 채택

- **프롬프트**: "처리 시간을 README에 기록할 때, 어떤 구간을 어떤 조건에서 재야 화면에 보이는 값과 맞고 믿을 만한 수치가 될까요?"
- **AI 응답**: `AnalysisService.analyze`의 `Stopwatch` 값을 기기 통합 테스트로 10회 반복 측정하고, 디버그가 아닌 프로파일 빌드로 실행한다. 테스트 이미지는 기기에서 직접 그려 사진 파일이 필요 없게 한다.
- **최종 결정**: 제안대로 측정하고, 첫 실행(모델 로드 포함)과 이후 실행을 나눠 기록합니다. 에뮬레이터 측정이라는 한계도 함께 적습니다.
- **이유**: README의 수치가 화면 표시와 일치해야 하고, 한 번 잰 값이나 디버그 빌드 값은 편차가 큽니다.

### 11. 온디바이스 검증 — 채택

- **프롬프트**: ""진짜 온디바이스"임을 무엇으로 증명할 수 있을까요? 기능이 동작하는지와 모델이 정확한지는 따로 봐야 하지 않을까요?"
- **AI 응답**: 비행기 모드를 켜고 네트워크가 실제로 끊겼는지 확인한 뒤, 앱을 직접 조작한 결과와 반복 측정을 모두 남긴다. 빨간 사과 오분류는 코드 문제가 아니라 모델 정확도 문제로 구분해 보고했다.
- **최종 결정**: 제안대로 검증하고 비행기 아이콘이 보이게 캡처합니다. 기능이 실행되는지와 모델이 맞히는지는 따로 기록합니다.
- **이유**: 코드에 네트워크 호출이 없다는 설명보다 실제 실행이 더 확실한 증거이고, 크래시 없이 동작해도 결과는 틀릴 수 있습니다.

## MP3 결정 사항

### 12. 공유 방식 — 채택

- **프롬프트**: "지금의 클립보드 복사가 "시스템 공유 시트로 다른 앱에 전달"에 해당할까요? 공유 시트로 바꾼다면 별도 인터페이스 없이 호출부를 하나로 모을 수 있을까요?"
- **AI 응답**: `share_plus`로 OS 공유 시트를 열고, `ShareService` 인터페이스 없이 상태 없는 함수 `shareResult` 하나를 결과 화면과 이력 화면이 함께 쓴다. 공유 시트가 열리는 것 자체가 피드백이므로 실패했을 때만 안내한다.
- **최종 결정**: 제안대로 적용합니다. 클립보드 복사는 제거하고, 공유에는 사진을 포함하지 않습니다.
- **이유**: 클립보드 복사는 다른 앱에 전달하는 동작이 아니며, 공유 시트에도 복사 항목이 있어 기능이 줄지 않습니다.

### 13. 이력 저장 범위와 형식 — 채택

- **프롬프트**: "구조를 정리하면서도 기존 이력 JSON 형식을 유지하고, 원본 사진 없이 결과 텍스트만 저장하는 원칙을 지킬 수 있을까요?"
- **AI 응답**: 기존 JSON 형식을 바꾸지 않고, `imagePath`는 `toJson`에서 제외해 방금 분석한 결과의 미리보기에만 쓴다. 이전 형식의 데이터도 읽을 수 있는지 테스트로 확인한다.
- **최종 결정**: 분석 방식, 결과 텍스트, 처리 시간, 분석 시각, 신뢰도만 저장합니다.
- **이유**: 사진은 결과 텍스트보다 훨씬 민감하고 분석이 끝나면 필요 없으며, 경로만 남아도 사진을 다시 찾아갈 수 있습니다. 형식을 유지해야 이미 저장된 이력을 계속 읽을 수 있습니다.

### 14. 저장소 구조 — 채택

- **프롬프트**: "인터페이스를 없애더라도 이력 상태 관리와 파일 저장은 나눠 두는 게 맞을까요? 쓰이지 않는 코드가 남아 있지는 않을까요?"
- **AI 응답**: `AnalysisHistoryStore`(목록 상태와 작업 순서)와 `FileHistoryStorage`(임시 파일에 쓰고 교체)의 분리는 유지한다. 전체 점검에서 어디서도 호출되지 않는 전체 삭제(`clear`)를 찾았다.
- **최종 결정**: 분리를 유지하고, 파일 쓰기가 성공한 뒤에만 목록을 바꿉니다. 쓰이지 않는 전체 삭제는 제거했습니다.
- **이유**: 두 클래스는 실제로 다른 일을 하며, 과제가 요구하는 것은 목록과 개별 삭제이고 쓰이지 않는 코드는 유지하지 않습니다.

### 15. 임시 사본 삭제와 백업 제외 — 채택

- **프롬프트**: ""원본 사진을 저장하지 않는다"는 설명이 이력 파일뿐 아니라 캐시와 백업까지 포함해 실제 동작과 맞을까요?"
- **AI 응답**: 사진 선택기가 앱 캐시에 사본을 남기고 있다(Android는 사진 한 장당 두 개). 사진을 바꾸거나 화면을 나갈 때 사본을 지우고, `android:allowBackup="false"`로 이력이 계정 백업에 올라가지 않게 한다.
- **최종 결정**: 제안대로 적용합니다(`ImageInputService.discard`). 갤러리의 원본은 건드리지 않습니다.
- **이유**: 이력에 사진을 넣지 않아도 캐시에 사본이 남으면 "원본 사진을 저장하지 않는다"는 설명이 정확하지 않습니다.

### 16. 서버 동기화 — 보류

- **프롬프트**: "초기 계획에 있던 Firebase 기기 간 이력 동기화를 이번 과제에서 진행해야 할까요?"
- **AI 응답**: Firebase 기기 간 동기화는 이번 과제의 필수 범위가 아니므로 선택적인 후속 항목으로 남긴다.
- **최종 결정**: 구현하지 않고 후속 항목으로 남깁니다.
- **이유**: 결과를 서버에 올리면 "기기 안에만 저장한다"는 원칙을 다시 설계해야 합니다.
