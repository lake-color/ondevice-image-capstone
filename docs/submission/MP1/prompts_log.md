# 프롬프트 기록

AI 도구와 논의하면서 정한 주요 결정 사항입니다. 지시와 수행 내역이 아니라, 논의 끝에 채택하거나 고친 결정만 담았습니다.
각 결정에는 논의의 출발이 된 주요 프롬프트의 요지, AI 응답, 그 응답을 어떻게 채택·수정했는지(최종 결정)와 이유를 적었습니다.

- **사용 도구**: Claude Code (Anthropic). 다른 AI 도구는 사용하지 않았습니다.
- **프롬프트**: 작업을 시킨 문장이 아니라 무엇을 검토하고 판단하려 했는지를 요약했습니다.
- **구분**: 채택은 AI 응답을 받아들인 것, 수정은 조건을 바꿔 받아들인 것, 기각 후 수정은 AI 응답을 받아들이지 않고 다른 방법을 정한 것, 보류는 이번에 하지 않기로 한 것입니다.
- **구성**: 단계마다 앞 단계의 결정에 그 단계의 결정을 더합니다.

## MP1 결정 사항

### 1. 구조 단순화 — 수정

- **프롬프트**: "구현체가 하나이고 추가 구현 계획도 없는데 인터페이스를 유지할 실질적인 이점이 있을까요? 파일 수를 줄이는 게 목적이 아니라, 필요한 책임 분리는 지키면서 실행 흐름을 설명하기 쉽게 만드는 게 목적입니다."
- **AI 응답**: 교체 계획이 없는 인터페이스 5개는 제거해도 된다. Dart는 모든 클래스가 인터페이스 역할을 하므로 테스트 대역은 구현 클래스를 `implements`해서 만들면 된다.
- **최종 결정**: 인터페이스는 제거하되, ViewModel·Controller 같은 새 계층은 넣지 않고 기존 Page + Service 구조와 실제 책임 분리는 유지합니다.
- **이유**: 과제 범위와 기술이 확정되어 있어 교체를 위한 추상화가 필요 없고, 계층이 적어야 실행 흐름을 설명하기 쉽습니다.

### 2. 예외와 오류 문구 — 채택

- **프롬프트**: "분석 오류는 공통 타입으로 묶되 권한·입력·저장 오류의 구분은 남기는 게 맞을까요? 검토에서 나온 권한 안내 문구 오류와 플랫폼 원문 노출 문제도 같이 봐야 할 것 같습니다."
- **AI 응답**: 사용자에게 그대로 보여줄 수 있는 `message`를 가진 `AppException`을 기반으로 예외를 `domain/exceptions.dart`에 모으고, 권한 거부(`ImagePermissionDeniedException`)와 그 밖의 입력 실패(`ImageInputUnavailableException`)를 나눈다. 플랫폼 원문 대신 한국어 안내를 보여주고, 권한 문구는 거부된 경로에 맞춘다.
- **최종 결정**: 제안대로 적용합니다. 화면에는 사용자용 한국어 문구만 표시합니다.
- **이유**: 권한 거부는 설정으로, 입력 실패는 다시 시도로 안내해야 해서 사용자가 할 일이 다르고, 영어 원문은 사용자에게 도움이 되지 않습니다.

### 3. 권한 요청 방식 — 채택

- **프롬프트**: "에뮬레이터에서 권한 거부가 재현되지 않는데, 과제가 요구하는 권한 요청 흐름을 실제로 보여주려면 무엇이 빠져 있는 걸까요?"
- **AI 응답**: 매니페스트에 `CAMERA`가 선언되지 않아 시스템이 권한을 묻지 않는 것이므로 선언을 추가한다. 카메라가 없는 기기도 설치되도록 `android.hardware.camera`는 `required="false"`로 둔다. Android 갤러리는 시스템 선택기가 고른 사진만 넘겨주므로 저장소 권한은 선언하지 않는다.
- **최종 결정**: 제안대로 적용합니다. 권한은 앱 시작 시가 아니라 사용자가 "카메라로 촬영"을 고른 시점에 요청합니다.
- **이유**: 필요한 순간에 필요한 권한만 요청해야 사용자가 이유를 이해합니다.

### 4. 권한 거부 안내와 설정 이동 — 수정

- **프롬프트**: "MP1의 "거부 시 안내 화면(설정 이동 안내 포함)" 기준에 비춰 보면, 창만 닫는 지금의 설정 버튼으로 충분할까요?"
- **AI 응답**: 설정 화면을 실제로 여는 방법과 문구로 경로만 안내하는 방법이 있다. 실제로 열려면 `app_settings` 패키지를 쓴다.
- **최종 결정**: 둘 중 하나가 아니라 둘 다 적용합니다. 버튼으로 이 앱의 설정 화면을 열고, 안내 문구에도 "설정 > 권한 > 카메라" 경로를 적습니다. 설정을 열지 못하면 직접 변경하라고 안내합니다.
- **이유**: 한 번 거부하면 OS가 다시 묻지 않을 수 있어 설정 이동이 유일한 복구 경로이고, 설정 화면이 열리지 않는 기기에서도 길을 알려줘야 합니다.

### 5. 권한 설명 문구 위치 — 채택

- **프롬프트**: ""권한이 왜 필요한지 설명하는 문구"를 별도 화면 없이 권한을 요청하기 직전에 보여줄 수 있는 자리는 어디일까요?"
- **AI 응답**: 시스템 권한 대화상자가 뜨기 직전 단계인 사진 가져오기 시트의 각 항목 아래에 이유를 적는다.
- **최종 결정**: 카메라 항목에 "촬영을 위해 카메라 권한을 요청해요. 사진은 기기 안에서만 사용합니다.", 갤러리 항목에 "직접 고른 사진 한 장만 앱에 전달됩니다."를 표시합니다.
- **이유**: 별도 설명 화면을 추가하지 않고도 요청 직전에 이유를 알릴 수 있습니다.

### 6. 단계별 제출물 구성 — 기각 후 수정

- **프롬프트**: "MP1과 MP2는 단계별로 제출하는데, 최종 코드를 그대로 낼까요, 단계 범위만 남긴 소스를 낼까요? 단계가 올라갈수록 코드와 문서가 더해지기만 하는 구조로 맞출 수 있을까요?"
- **AI 응답**: 최종 코드를 그대로 제출하고 README에서 단계별 범위만 설명한다. 이후 단계별 소스를 비교한 뒤에는, 앞 단계에만 있는 것을 루트로 옮기고 다음 단계에서 삭제만 해서 앞 단계를 만들자고 제안했다.
- **최종 결정**: 첫 제안은 받아들이지 않았습니다. 단계마다 그 단계 범위의 소스를 제출하되, MP3는 루트와 같게 두고 MP2는 MP3에서, MP1은 MP2에서 다음 단계의 코드를 삭제만 해서 만듭니다. README와 이 기록도 같은 방식으로 앞 단계 내용에 더해 갑니다. 스크린샷은 제출 규칙(한 폴더, 화면 순서 번호, 최대 12장)에 맞춰 단계마다 `screenshots/` 한 폴더에 모으고, 단계마다 그 단계 평가 기준에 필요한 화면만 골라 앞 단계 화면에 더합니다(MP1 4장, MP2 7장, MP3 10장). 단계마다 평가 기준은 그대로 충족해야 합니다.
- **이유**: 앞 단계에서 보이던 기능이 다음 단계에서 사라지거나 같은 코드가 단계마다 다르면, 이어서 개발했다고 설명하기 어렵습니다.
